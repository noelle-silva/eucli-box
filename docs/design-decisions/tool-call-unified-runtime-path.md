# 工具调用统一底层主路事实要求

## 事实要求

工具调用只有一条底层主路；文本和原生只是两个入口，只有入口、原始事实位置、客户端呈现不同；其他过程必须同源同路。

这是工具调用体系的事实要求，不是建议，也不是展示层偏好。任何实现、重构、修复、文档补充都必须让最终结果保持这个事实。

## 适用范围

本文约束两种工具调用方式：

- 文本协议工具调用：助手把工具请求写在自己的回复正文里。
- 原生工具调用：模型通过供应商或运行时的专门通道发起工具请求。

本文约束完整链路：触发、识别、执行、确认、等待、结果、错误、取消、继续回答、事实保存、历史再使用、客户端呈现。

## 唯一底层主路

工具主路只负责一件事：把已经识别出的工具请求执行完，并把工具结果交还给运行时，让助手继续完成回答。

进入主路后，不得再因为请求来自文本入口或原生入口而分出两套执行规则。以下过程必须同源同路：

- 工具权限判断。
- 工具确认流程。
- 工具等待状态。
- 工具执行调度。
- 工具失败处理。
- 工具取消处理。
- 工具结果接收。
- 工具结果交还给助手继续回答。
- 工具结果参与后续历史上下文的有效信息投影。

如果某个过程在文本入口和原生入口之间出现分叉，必须证明这个分叉只服务于入口、原始事实位置或客户端呈现。无法证明时，该分叉视为体系偏移。

## 允许不同的三处

两种工具调用只允许在三处不同。

### 1. 入口不同

文本协议工具调用的入口是助手正文。运行时可以临时读懂正文里的工具请求，把它转换为本轮执行需要的工具意图。

原生工具调用的入口是专门通道。运行时直接接收结构化工具请求。

入口差异到此为止。入口完成识别后，二者必须汇入同一条工具主路。

### 2. 原始事实位置不同

文本协议工具调用的请求本体属于助手正文。正文里的工具请求文字就是它的原始事实位置。

原生工具调用的请求本体不属于助手正文。它来自专门通道，所以需要独立保存请求事实。

工具结果无论来自哪种入口，都属于工具结果事实。结果可以独立保存，并可以和对应请求建立关联，但不能替代、复制或伪装成请求本体。

### 3. 客户端呈现不同

文本协议工具调用的客户端呈现，应以助手正文为事实主线，把正文中的工具请求翻译成用户可理解的请求卡片，并把对应工具结果展示在附近。

原生工具调用的客户端呈现，可以把独立请求和独立结果成组展示。

客户端呈现只负责翻译和摆放，不得反向改变事实保存，不得决定历史再使用，不得让显示状态成为运行时语义。

## 根系涌现原则在本问题中的体现

工具调用体系不是通过新增一个“文本工具调用管理器”或“统一工具调用控制中心”拼出来的。它应该从以下根节点职责自然涌现：

- 助手正文负责保存助手真实说过的话。
- 原生请求记录负责保存专门通道发起的请求事实。
- 入口识别负责把不同来源的请求读成一次临时执行意图。
- 工具主路负责执行意图、产生结果、交还运行时。
- 工具结果记录负责保存外部工具返回的事实。
- 历史投影负责把真实历史整理成模型可理解的有效材料。
- 客户端呈现负责把真实事实翻译成用户可理解的画面。

当这些根节点职责清楚后，复杂行为应自然涌现：文本工具和原生工具都能执行、都能返回结果、都能继续回答、都能被展示、都能进入历史理解。这个复杂结果不需要额外制造第二套工具链路。

## 禁止方向

以下方向违反本文事实要求：

- 为文本协议工具调用新增独立执行主路。
- 为了文本协议工具调用反向修改底层工具主路的语义。
- 把文本协议工具请求持久化成原生工具请求事实。
- 把原生工具请求伪装成助手正文。
- 把工具结果塞回助手正文，让它看起来像助手自己写出的文本。
- 让客户端隐藏、折叠、编辑状态反向决定运行时事实或历史投影。
- 为了遮住协议文本、空白回复或工具小票污染而新增兜底遮罩机制。
- 用补丁式过滤代替事实位置、入口职责和主路职责的重新归位。

## 历史再使用要求

历史再使用必须保留真实来路，但主路语义必须一致。

文本协议工具调用的历史应表达为：助手当时在正文里写出了工具请求，工具主路执行后返回了结果。

原生工具调用的历史应表达为：模型当时通过专门通道发起了工具请求，工具主路执行后返回了结果。

二者都应让模型理解同一件核心事实：工具被请求、工具被执行、工具返回了结果、助手应基于结果继续完成回答。

历史投影不得把文本入口转换成原生入口，也不得把原生入口转换成文本入口。

## 客户端呈现要求

客户端呈现必须服务事实，而不是制造事实。

文本协议工具调用可以把正文里的协议文字渲染为请求卡片，但这只是展示翻译。真实正文仍然保留原始请求文字。

原生工具调用可以把独立请求和结果作为工具组展示，但这只是展示组合。真实请求仍然来自专门通道。

工具结果必须明确呈现为工具结果，不能显示成助手正文的一部分。

## 验收设问

每次修改工具调用链路，都必须回答以下问题：

1. 修改后，工具调用是否仍然只有一条底层主路？
2. 文本入口和原生入口是否只在入口、原始事实位置、客户端呈现三处不同？
3. 工具确认、执行、失败、取消、结果、继续回答是否仍然同源同路？
4. 文本协议请求是否仍然属于助手正文，而不是被保存成原生请求事实？
5. 原生工具请求是否仍然属于专门通道事实，而不是被伪装成助手正文？
6. 工具结果是否仍然是独立结果事实，而不是被塞回助手正文？
7. 客户端呈现是否只是翻译和摆放，而没有反向决定事实保存或历史投影？
8. 修改方向是否符合根系涌现：通过清晰根职责的协作产生完整行为，而不是新增抽象管理器、兜底遮罩或第二套工具链路？

如果任一问题答案是否定的，修改不能合入，必须回到根职责重新规划。

## 最终结果要求

最终实现必须达到以下状态：

- 一条工具主路。
- 两个触发入口。
- 三处允许差异。
- 请求事实按来源保真。
- 工具结果独立保存。
- 历史投影保留真实来路。
- 客户端只做事实翻译。
- 复杂工具行为由根节点职责自然涌现。

这就是本问题里根系涌现原则的验收标准。
